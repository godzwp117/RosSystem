# M1 可信数据采集与标签规范

> 分支：`research/m1-trusted-action-retraining`
> 基准：`86a8910bf4560dfe455bec09bc503600c30bf670`
> run_id：`m1retrain-20261020T023546Z`
> 采集组件：`scripts/m1_session_collector.py`、`scripts/m1_collect_sessions.py`
> 环境：容器 `rg_m1r`，ROS 2 Jazzy，Domain 68

本规范先于数据产生而写定，之后的数据与模型都必须遵守它。
**它不能为了迁就结果而修改**；如需改动，必须新开 run_id 重采。

## 1. 什么是"独立采集会话"

一个**独立采集会话（session）**= 一次由单一实验条件驱动、
有明确开始与结束、期间实验条件不变的连续观测。

判定为独立会话的充分条件（全部满足）：

1. 由一次显式的采集进程调用产生，进程启动/结束时间被记录；
2. 期间**实验条件恒定**（发布频率/模式、图行为、是否违规）；
3. 与其它会话**不共享采集进程**，也不共享其窗口；
4. 会话 ID 全局唯一，格式 `<label>-<scenario>-<run>`。

**一个窗口不是独立会话。** 同一会话内的相邻窗口高度自相关，
把它们当独立样本会严重高估泛化能力。

## 2. 会话如何分组

分组键 = `session_id`。所有按会话划分的评估（GroupKFold、留一会话）
都以它为单位，**绝不**以窗口或行为单位。

## 3. 会话开始与结束的依据

| 边界 | 依据 |
| --- | --- |
| 开始 | 采集进程完成 rclpy 初始化并建立订阅之后，记录 `started_at`（UTC，毫秒） |
| 结束 | 达到 `--duration` 后 flush 未闭合窗口，记录 `ended_at` |

窗口以**单调时钟**（`time.monotonic()`）切分，避免系统时钟跳变影响区间长度；
`started_at`/`ended_at` 用墙钟，仅用于审计与关联，不参与特征计算。

## 4. 窗口长度

**30 秒，固定。** 依据：

* 与既有部署契约一致（`ros2_window.py` 的 `TRAINING_WINDOW_MS = 30000`，容差 20 个百分点）；
* 低频正常流量（2 Hz）在 10 秒窗口内只有约 20 条样本，间隔统计不稳定；
  30 秒给出约 60 条，`gap_p95` 才有意义；
* 成本：**检测延迟下界约 30 秒**。对"导航请求准入"这类秒级决策，
  M1 只能提供**历史行为风险**，不能对当前请求做实时拦截判断。

## 5. 滑动步长

**无重叠，步长 = 窗口长度。** 理由：重叠窗口会在训练/测试之间制造
"同一批消息出现在两个窗口"的泄漏，并使有效样本数虚高。

## 6. 时间边界

区间为**左闭右开** `[start, end)`：恰好落在边界上的消息归入后一个窗口，
不会重复计入；窗口首尾相接，`window_end` = 下一个 `window_start`。

## 7. 时间同步与误差

* 所有间隔基于**同一进程的单调时钟**，不存在跨主机时钟偏移问题；
* 误差来源：订阅回调调度抖动。50 Hz 实测 `gap_median = 20.00 ms`
  （理论 20.00 ms），抖动在 0.5 ms 量级；
* 传输延迟会造成到达间隔抖动，这是真实观测的一部分，不做平滑或修正。

## 8. 事件覆盖完整性

每个窗口记录 `samples` 与 `status`：

* `samples >= MIN_SAMPLES(10)` → `OK`，给出特征；
* 否则 → `INSUFFICIENT_OBSERVATION`，**不编造数值**，且计入 `insufficient_windows`。

**不得**把不足窗口当作正常样本。

## 9. 标签产生来源

标签**只**来自实验条件，字段 `label_source = EXPERIMENT_CONDITION`，
并附 `label_basis` 文字说明，例如：

* `"authorized 500 Hz publisher; high rate alone is not a violation"` → `normal`
* `"unbounded topic flood at 2000 Hz, far beyond any authorized workload"` → `anomaly`

**硬性约束**：`model_used_for_labeling` 恒为 `false`。
模型预测绝不参与标签生成；采集脚本不读取任何模型输出。

## 10. 正常与异常的定义

| 类别 | 定义 |
| --- | --- |
| `normal` | 行为在系统授权范围内：无论频率高低、是否突发、是否重启，只要不违反安全策略即为正常 |
| `anomaly` | 存在**定性**的安全违规事实（非授权负载、异常发现行为、侦察行为），而不是"频率比别人高" |

特别规定：**500 Hz 正常发布者是 `normal`**。把高频一律标为攻击会让模型
学到一条无意义的频率阈值，并在真实高负载业务下产生大量误报。

## 11. 受控实验数据与真实运行数据的区分

本轮数据**全部是受控实验**（隔离 Domain 68、由实验脚本驱动）。
字段 `label_source=EXPERIMENT_CONDITION` 与 `collector` 路径共同标识来源。

**不得**把本轮数据描述为"生产真实流量"。

## 12. 采集错误与 UNKNOWN

| 情况 | 处理 |
| --- | --- |
| 样本不足 | 窗口标 `INSUFFICIENT_OBSERVATION`，模型侧视为 UNKNOWN，不得当作 NORMAL |
| 采集进程非零退出 | 整个会话作废并记录，不进入训练 |
| 图查询异常 | `graph_change_count` 记为 0 会**低估**异常，须在审计中标出 |
| 会话中途断流 | `gap_max_ms` 会显著增大；不得据此自动标 anomaly |

## 13. 是否能够关联实际 Action

**当前不能。** 本采集器观测的是**话题消息**，不是 Action `send_goal`。
M2 研究接口 `trusted-action-events/1` 截至共同基准只证明过自定义
`CandidateTask` 入口，**没有**证明捕获 Gateway 真实 SendGoal。

因此本轮计数语义严格写作"话题消息数"，
**不得**重命名为 `action_send_goal_received_count`。详见
`docs/research/M1_TRUSTED_ACTION_FEATURES.md`。

## 14. 原始数据如何核验

* 每个会话一个 JSON，含会话元数据 + 全部窗口；
* 采集清单 `collection_manifest.json` 记录每个会话的命令、返回码、窗口数；
* 全部证据生成 `SHA256SUMS.txt` 并可 `sha256sum -c` 复核；
* 窗口特征可由原始 `samples` 与窗口定义**独立复算**（见 §15 的复算测试）。

## 15. 如何避免训练/测试泄漏

| 泄漏渠道 | 本轮措施 |
| --- | --- |
| 窗口时长编码标签 | **不使用 `duration_ms` 作为特征**（窗口固定，本就无信息） |
| 会话 ID / 文件名 / 场景编号 | 不作为特征 |
| 资源名编码类别 | 不作为特征 |
| 相邻窗口跨训练/测试 | 按 `session_id` 分组划分，同会话窗口只出现在一侧 |
| 重叠窗口共享消息 | 窗口不重叠 |
| 标签来源字段 | 元数据，不进入特征 |
| 后验结果（Gateway/执行） | 采集时不存在，也不采集 |
| 数据生成器差异 | 每个会话记录 `collector` 与参数，训练审计里检查 |
| 单特征捷径 | 训练前做单特征分类能力与相关性审计，任一特征单独达到过强判别力即告警 |

### 强制泄漏审计（训练前必跑）

1. 每个特征与标签的 AUC / 单特征 F1；
2. 特征-标签互信息；
3. 训练/验证会话重叠检查（必须为空交集）；
4. 窗口重复检测（特征向量完全相同的计数）；
5. 特征消融（去掉任一特征后指标变化）；
6. 跨频率、跨会话、跨资源的迁移检查。

任一环节失败即**不得**声称模型有效。
