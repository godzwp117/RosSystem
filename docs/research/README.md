## CASE-A：上游全部放行仍被权威策略阻断

| 项 | 内容 |
| --- | --- |
| **触发条件** | 三个研究模块（通信/身份/任务）全部输出允许建议；候选目标 `(5.0, 5.0)` 超出 `config/task_policy.yaml` 允许区域 `x,y∈[0,4]` |
| **预期** | 适配层判 READY，但真实 Gateway 必须阻断 |
| **实际** | 适配层 `READY_FOR_GATEWAY_SUBMISSION`；Planner 实际提交；Gateway `DecisionEvent` = `BLOCK` / `OUT_OF_REGION`（detail：`target (5.0, 5.0) outside allowed_region`）；`ExecutionEvent` 数 **0**；NavigationSim journal 行数 **0** |
| **首次失败证据** | 无（一次通过；但第二批复核时发现该结论当时由 T14 的恒真断言支撑，见 CASE-D） |
| **根因** | 架构上研究模块只产出建议，准入判定唯一由 SecurityGateway 依据权威策略做出 |
| **修复** | 无需修复；属设计预期 |
| **回归** | T03 在第三批全量验收中再次通过（15/15 之一） |
| **Git SHA** | 起始 `1eb172a`；第三批复测 `046e474` |
| **环境** | ROS 2 Jazzy / `rmw_fastrtps_cpp` / Domain 42 / 容器 `rg_jazzy` |
| **结论适用范围** | 单机单容器、单一中间件实现；**不得**外推为跨主机或跨 RMW 的等价结论 |
| **证据** | `tests/evidence/e1_T03/team_handoff/T03/`（`assertions.json`、`gateway_audit.jsonl`、`navsim_goals.jsonl`） |

## CASE-B：上游阻断与 Gateway 阻断的层级区分

| 项 | 内容 |
| --- | --- |
| **触发条件** | 身份模块输出 `DENIED`（另有通信 `SUSPICIOUS`、任务 `BLOCK_RECOMMENDED`、非法 JSON、模块崩溃、`request_id` 不一致、版本不兼容） |
| **预期** | 适配层本地阻断，**不启动 Planner**，Gateway 中不存在该 `request_id` 的任何记录 |
| **实际** | `decision=ADAPTER_BLOCK`；`online.submitted=false`；Gateway DecisionEvent 数 **0**；NavigationSim Goal 增量 **0**；原因码全部为 `ADAPTER_` 前缀 |
| **根因** | 适配层在启动 Planner 之前完成全部校验；阻断路径不产生任何下游副作用 |
| **修复** | 无需修复 |
| **回归** | T04–T08、T12、T13 在第三批全量验收中全部通过 |
| **Git SHA** | `046e474` |
| **环境** | 同上 |
| **结论适用范围** | 同上；且**不得**把适配层阻断伪造成 Gateway BLOCK —— 本案例正是为此提供对照 |
| **证据** | `tests/evidence/e1_T04…T13/` |

> **为什么这条重要**：两种阻断在日志上可能"看起来都是拒绝"，
> 但安全含义完全不同——一个是策略判定，一个是流程未进入。
> 混淆二者会得出错误的系统能力结论。

## CASE-C：故障注入静默失效导致的失败开放

| 项 | 内容 |
| --- | --- |
| **触发条件** | 测试通过**模块专属**控制块请求协议层故障注入：`{"comm_risk": {"fault": "invalid_json"}}` |
| **预期** | 模块输出非法 JSON → 适配层阻断，请求不进 Gateway |
| **实际** | 适配层返回 **READY**，请求**真的到达 Gateway 并执行成功**（T07/T08 首轮 FAIL） |
| **首次失败证据** | `tests/evidence/d2_T07/`、`d2_T08/`（当时 `decision=READY_FOR_GATEWAY_SUBMISSION`、`delta=1`） |
| **根因** | `mock_modules/_protocol.py` 的 `control_for()` 在 `update(模块专属控制块)` **之后**又执行 `control['fault'] = raw.get('fault')`，把已设好的值覆盖成 `None` |
| **修复** | 按"模块专属 > 顶层按模块 > 顶层标量"显式确定优先级，保证不被覆盖 |
| **回归** | 修复后 T07/T08 转为 PASS（原因码 `ADAPTER_MODULE_STDOUT_INVALID` / `..._EXIT_NONZERO`），且第三批全量验收再次通过 |
| **Git SHA** | 引入 `157b148`；修复 `5751637` |
| **环境** | 同上 |
| **结论适用范围** | **测试脚手架缺陷**，不是产品缺陷；但它导致的**失效方向是失败开放**，对任何安全测试框架都适用 |
| **证据** | `tests/evidence/d2_T07|d2_T08/`（修复前）、`e1_T07|e1_T08/`（修复后） |

> **最有价值的一点**：**79 项离线单测当时全部通过**——因为它们一直使用顶层
> `fault` 形式，恰好绕开了这条分支。这说明"离线全绿"不能替代在线入口回归。

## CASE-D：恒真断言支撑的虚假 PASS

| 项 | 内容 |
| --- | --- |
| **触发条件** | T14 检查审计文件是否存在，写法为 `os.path.isfile(item_audit) or True` |
| **预期** | 文件不存在时必须 FAIL |
| **实际** | **无论文件是否存在都通过**。第二批据此把 T14 记为 PASS —— 该 PASS 不成立 |
| **首次失败证据** | 缺陷在第三批复核时由代码审查发现（非运行失败），故无失败日志；反向验证证据见下 |
| **根因** | `X or True` 恒为真；断言退化为空操作 |
| **修复** | 删除恒真逻辑，改为读取真实审计/下游日志并逐项断言（文件缺失、坏行数、请求未关联均 FAIL）；`--scenario all` 同时修复遗漏的 T10/T11 |
| **回归** | 新增 8 项反向验证（缺文件/缺 request_id/串扰/坏行必须失败）全部通过；AST 复核全仓库测试代码恒真断言 **0 处**；T14 重写后 28 项断言通过 |
| **Git SHA** | 引入 `1eb172a`；修复 `165bb06` |
| **环境** | 同上 |
| **结论适用范围** | 通用测试可信性问题：**"测试通过"与"断言有效"是两件事** |
| **证据** | `tests/unit/test_handoff_assertions.py`、`tests/evidence/e1_T14/` |

> 修复过程中，检查器自身也出现过同类问题：首版用文本匹配，把文档字符串里
> **描述该缺陷的说明文字**误判为代码。改用 AST 检测后消除。
> 这说明**检测手段本身也需要被验证**。

## CASE-E：模块输出资源异常与受控终止

| 项 | 内容 |
| --- | --- |
| **触发条件** | 模块持续向 stdout 洪泛输出（64 MiB） |
| **预期** | 适配层**在读取过程中**限流，不得先完整缓冲再检查长度 |
| **实际** | 旧做法（`communicate()` 全读后检查）峰值 RSS **139 MB**；新做法峰值 **27 MB** 并立即终止该进程组 |
| **首次失败证据** | 无运行失败；通过峰值内存对照测量暴露 |
| **根因** | `communicate()` 先把 stdout/stderr 全部读入内存，长度检查发生在之后，`max_stdout_bytes` 形同虚设 |
| **修复** | 新增 `read_bounded()`：selector 边读边计数；stdout 超限立即终止本进程组；stderr 继续排空但只保留前 N 字节（排空必要，否则子进程被管道堵死） |
| **回归** | D1 专项测试 58→79 项；独立复核 43→59 项；洪泛用例断言具体原因码与清理结果 |
| **Git SHA** | 修复 `ee34341` |
| **环境** | 同上 |
| **结论适用范围** | 通用子进程安全：**输出上限必须在读取路径上实施，而不是在读取之后校验** |
| **证据** | `docs/review/F0_D2_…` §1；`tests/evidence/d1_review/review_result.json` |

## CASE-F：审计写入失败触发失败关闭

| 项 | 内容 |
| --- | --- |
| **触发条件** | 适配层审计日志写入失败（四种：路径是目录、父路径是普通文件、`ENOSPC`(`/dev/full`)、只读伪文件系统） |
| **预期** | 不得继续返回可进入提交流程的结论 |
| **实际** | 修复前：仅写 stderr 诊断，此前得到的 `READY` **不受影响**；修复后：全部降级为 `ADAPTER_BLOCK` + `ADAPTER_AUDIT_WRITE_FAILED` |
| **根因** | 审计写入是"事后记录"，不是推进的前置条件 |
| **修复** | 审计写入成为推进前置条件（先写审计、再据其成败决定结论）；`append_log` 返回 `(ok, detail)` 并 `fsync` |
| **回归** | 四种故障全部阻断；独立复核新增对应检查 |
| **Git SHA** | 修复 `ee34341` |
| **环境** | 说明：容器内以 **root** 运行会绕过权限位，故未用 `chmod` 模拟"无写权限"，改用 root 也无法写入的目标 |
| **结论适用范围** | 通用审计可靠性；**不得**把适配层审计失败与 Gateway 审计失败混为一谈（原因码独立） |
| **证据** | `docs/review/F0_D2_…` §1 H2 |

## CASE-G：依赖供给静默降级

| 项 | 内容 |
| --- | --- |
| **触发条件** | 用 `ros:jazzy` 基础镜像新建容器（不带 `jsonschema`） |
| **预期** | 环境准备应明确失败并给出修复指引 |
| **实际** | 全新成员容器**根本无法运行适配层**，报错是无法定位的 `TypeError: 'NoneType' object is not callable`；且 `container_up.sh` 的 `\|\| true` 把安装失败**吞掉**，调用方仍以为环境就绪 |
| **首次失败证据** | T14 首轮失败；容器内 `import jsonschema` 抛 `ModuleNotFoundError` |
| **根因** | 依赖只存在于某个长期容器（早先手工装过一次），供给路径未落实；失败被 `\|\| true` 掩盖 |
| **修复** | 新增 `scripts/check_deps.sh` 做真实能力检查（导入可用 + 真实具备 `Draft202012Validator` + **严格 RFC 3339 检查器自检通过**）；`container_up.sh` 两条路径改为失败即 `exit 5`；提供显式逃生开关并警告 |
| **回归** | 缺依赖容器返回 **5** 并打印安装命令；具备依赖返回 0 |
| **Git SHA** | 修复 `3e1d108` |
| **环境** | 同上 |
| **结论适用范围** | 通用环境可复现性：**"在我机器上能跑"必须落实为可判定的供给步骤** |
| **证据** | `scripts/check_deps.sh`；`docs/review/F0_核心阻塞项修复验收报告.md` §2 A6 |

## CASE-H：跨实例清理误伤风险

| 项 | 内容 |
| --- | --- |
| **触发条件** | 测试脚手架执行预清理 `reap_stragglers()`，而同一容器内存在其他实例的 Gateway/NavigationSim |
| **预期** | 只清理属于本实例的进程 |
| **实际** | 原实现扫描 `/proc` 后对所有匹配工作区路径标记的进程直接 SIGKILL，**不区分 ROS Domain、不区分启动者**；`reliability_check.py` 直接复用 |
| **首次失败证据** | 代码审查发现；随后运行时可见 `[preflight] 跳过 N 个不属于本实例的节点进程` |
| **根因** | 归属判定依据是"进程名/工作区路径"，而不是可证明的实例标识 |
| **修复** | 测试启动的节点注入专属标记 `RG_TEST_RUN_ID`；清理只作用于**带标记**或**本会话**的进程，其余只报告不清理 |
| **回归** | **安全属性实测**：启动一个不带标记的栈（6 个节点），执行 `reap_stragglers` 后仍为 6 个节点、`reaped=[]` |
| **Git SHA** | 修复 `3e1d108` |
| **环境** | 同上 |
| **结论适用范围** | 多成员共享环境下的通用测试隔离问题 |
| **证据** | `docs/review/F0_核心阻塞项修复验收报告.md` §2 A5 |

## CASE-I：跨 Domain 就绪探测的缓存依赖

| 项 | 内容 |
| --- | --- |
| **触发条件** | 在多个 ROS Domain 之间切换后执行就绪探测 |
| **预期** | 探测结果应反映**当前** Domain 的真实图 |
| **实际** | 原实现用 `ros2 action list`，经共享 ROS 2 daemon 查图，而 daemon 按 Domain 缓存 |
| **首次失败证据** | **未能复现**。在 Domain 42 有栈的情况下切到 51 查询，返回为空，未出现假就绪或假失败；daemon 在本环境表现为按 Domain 正确隔离 |
| **根因** | 设计上存在"探测依赖带缓存的间接层"这一风险面 |
| **修复** | 改为本进程内 rclpy 直接探测（`tests/integration/domain_ready_probe.py`）：自建节点使图属于当前进程的 Domain，用 `ActionClient.wait_for_server()` 做真实可达性判断，不经 daemon，也不重置或杀死他人 daemon |
| **回归** | Domain 42 无栈→`NOT_READY`；有栈→`READY`；同一时刻 Domain 51→`NOT_READY`；切回 42→`READY` |
| **Git SHA** | 修复 `94b65be` |
| **环境** | 同上 |
| **结论适用范围** | **中**。修复本身已验证有效；但"原始缺陷确实存在且被修复"这一更强结论**未被证据支持**，故只记为"消除了对 daemon 缓存的依赖" |
| **证据** | `docs/review/F0_D2_…` §3 |
