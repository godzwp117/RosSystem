## 0. 开场（约 40 秒）

> 我们的课题是《面向具身智能机器人的 ROS 2 通信可信分析与动态最小权限防护系统》。
>
> 它要解决的核心矛盾是：**具身智能机器人必须执行任务，但执行任务的链路本身可能被
> 越权利用。** 我们要证明的不是"我们能检测所有攻击"，而是——
> **在不信任任何单一组件的前提下，系统仍然只在证据充分时才执行，并且每一步都可审计。**

---

## 1. 研究问题与三个模块的分工（约 90 秒）

> 我们把"一条导航任务该不该执行"拆成三个互相独立的证据维度：
>
> - **M1 通信风险**：这次通信行为像不像正常行为；
> - **M2 身份与权限**：这个主体历史上被授权过什么，当前请求的身份能否绑定；
> - **M3 任务风险**：这个目标任务本身是否越出策略边界。
>
> 三个模块**只输出证据与建议**，都不拥有执行许可。
>
> 这是刻意的设计——**任何单一模块被攻破或被误判，都不能直接导致执行。**
> 执行许可在下一层。

---

## 2. 安全分层架构（约 90 秒）

> 从上到下四层，每一层的信任假设都不同：
>
> 1. **DDS-Security**：通信层原生身份与权限，由 Fast DDS 强制执行，我们的应用改不了它；
> 2. **三个研究模块**：只给建议；
> 3. **F0 适配层**：做 Schema、关联字段、证据来源校验，**失败关闭**；
> 4. **SecurityGateway**：唯一权威的业务准入，按正式 TaskPolicy 判 ALLOW / BLOCK。
>
> 三个不变式请记住：
>
> - `READY_FOR_GATEWAY_SUBMISSION` **不是** Gateway 允许；
> - Gateway 允许 **不等于** 导航执行成功；
> - 模块输出符合 Schema **不等于** 证据可信。
>
> 这三条不是口号，每一条我们都有对应的测试或在线证据。

---

## 3. 真实 M3 在线闭环（约 2 分钟，现场跑）

> 现在跑的是真实 M3 规则引擎进入在线链路。

```bash
./scripts/demo_20261019_release.sh --scenario m3 --run-id demo-20261019-m3
```

> 六个场景，我重点讲三个：
>
> **ON-01**：真实 M3 判"允许"，Gateway 也判 ALLOW，NavigationSim 真的收到 1 条 Goal。
> 这是正向链路。
>
> **ON-05 是最有说服力的一个**：M3 说"允许"，适配层也确实放行了，
> 但 Gateway 依据**未修改的正式策略**判了 `BLOCK / OUT_OF_REGION`，下游 Goal 为 0。
> **这就是"研究模块的建议不能取代权威准入"的实证。**
>
> **ON-03 / ON-04**：策略缺失给 `UNKNOWN`、策略损坏给 `ERROR`，两种都失败关闭，
> 下游零提交。
>
> 关于 **ON-06 Planner 超时**，我特别说明：超时**不代表**没执行，也**不代表**被拒绝。
> 是否到达 Gateway、是否 ALLOW、有没有 Goal，必须查这一次的审计日志。
> 我们累计四次不同运行，下游结果出现过 1、0、1、1——**所以绝不能预设。**

---

## 4. Gateway 的权威性与可审计性（约 60 秒）

> 请注意审计文件里的事件序列：
> `RosCommEvent → DecisionEvent → ExecutionEvent`，全部按 `request_id` 可关联。
>
> 这意味着任何一次执行都能回答三个问题：
> 谁请求的、Gateway 为什么这么判、下游到底执行了没有。
>
> 对机器人安全来说，**可追溯性和拦截能力同等重要**。

## 5. DDS 原生拒绝（约 90 秒，现场跑）

```bash
./scripts/demo_20261019_release.sh --scenario dds --run-id demo-20261019-dds
```

> 这一组跑在**另一个 Domain（43）**，启用 Enforce，和我们刚才的在线演示
> **不是同一次运行**，我不会把它们混着说。
>
> 重点是三个对照：
>
> - **S3**：`/planner` 身份直接访问 `/rg/nav_execute`，被 **DDS 原生权限拒绝**
>   ——不是我们的应用层拦的，是中间件在权限层拒绝的；
> - **S3C 正向对照**：同样是直连，`/gateway` 身份**成功**。
>   有正对照才能说明 S3 的拒绝是权限导致，而不是网络或代码碰巧失败；
> - **S6**：安全配置损坏时**不静默降级**为无认证通信。
>
> 这条边界是应用改不动的，也是我们"最小权限"主张的基础。

## 6. 三真实模块集成成果（约 90 秒，现场跑）

```bash
./scripts/demo_20261019_release.sh --scenario three-real --run-id demo-20261019-tr
```

> 现在三个模块**全部是真实程序**，不是 Mock：
>
> - `THREE_EXTERNAL_CALLED = PASS` —— 三个真实进程被调用；
> - `THREE_EXTERNAL_VALIDATED = PASS` —— 输出通过 Schema、`run_id`/`request_id`/`event_id`
>   关联、任务与资源一致性校验；
> - `THREE_EXTERNAL_ONLINE_PROCEED = BLOCKED` —— **这是正确的阻断，不是故障。**
>
> 为什么被阻断？因为真实证据不够：
>
> - M1 的真实模型**没通过验证门槛**，生产语义下只能给 `UNKNOWN`；
> - M2 能解释历史授权，但**拿不到当前请求的 DDS 身份绑定**——
>   ROS 2 在订阅端不暴露"这条消息的发布者是谁且已认证"；
> - 只有 M3 能给出 `ALLOW_RECOMMENDED`。
>
> 所以 F0 判 `ADAPTER_BLOCK`。**这正是"无可信证据不放行"在真实数据上生效。**

## 7. F0 身份防伪造（约 60 秒，现场跑）

```bash
./scripts/demo_20261019_release.sh --scenario f0 --run-id demo-20261019-f0
```

> 这是我们最近修掉的一个真实漏洞，值得单独讲。
>
> 修复前，F0 判断"当前请求身份"只读模块输出里的一个字段。
> 我们写了一个只会打印的模块，把 `status` 和整个 `checks` 字典都伪造成"通过"，
> F0 就给了 `READY_FOR_GATEWAY_SUBMISSION` ——**一次真实核验都没发生。**
>
> 修复后：原始证据、核验密钥、受信任签发者清单、防重放账本**全部**来自
> F0 的受信任本地配置，由 F0 自己核验签名、签发者、请求摘要绑定、新鲜度和 nonce。
>
> 现在裸 `AUTHENTICATED`、伪造完整 `checks`、历史授权、TEST_ONLY 签发者、
> 坏签名、重放、权限过宽的密钥——**全部阻断**，38 项测试。
>
> **必须说清**：这证明"F0 不再相信自报"，**不**证明"M2 已经具备真实
> DDS 身份认证能力"。这两件事不能混。

## 8. 当前限制（约 45 秒，主动说）

> 我主动说三个限制，避免误解：
>
> 1. **M1**：有 `/proc` 主机级采集器，但模型门槛未过，且部分 ROS 2/RTPS 特征仍缺失，
>    **尚未证明具备有效的在线通信攻击检测能力**；
> 2. **M2**：签名与防重放组件已具备，但**没有经过审核的生产 DDS 身份签发者**；
> 3. **演示主场景的 M1/M2 仍是 Mock**——这是受控演示，不代表三模块已能正向联合准入。
>
> 我们宁可把边界说清楚，也不想让"看起来能用"掩盖"证据不足"。

## 9. 下一步（约 40 秒）

> 两个专项并行推进，都从本次冻结的同一份代码基线出发：

> - **M1**：用交付的训练代码重训到达标，并建立 ROS 2 运行时特征采集映射；

## 10. 收尾（约 20 秒）

> 一句话总结：
>
> **我们做的不是"更强的检测器"，而是一条"证据不足就不执行、每一步都可审计"的
> 机器人执行链。** 检测能力会继续提升，但这条不变量不会放松。

## 附：常见提问与标准回答

| 提问 | 回答要点 |
| --- | --- |
| "三个模块都真实在跑吗？" | 三真实联合调用场景是**全部真实**（LEVEL 1/2 PASS）；**在线演示主场景**的 M1/M2 是 Mock，M3 真实。两者必须分开说。 |
| "为什么不让三个真实模块跑通正向？" | 缺的是**可信当前证据**：M1 模型门槛未过、M2 无当前身份绑定。系统按设计拒绝，不能靠伪造达成。 |
| "超时了算失败吗？" | 不算。超时是客户端没等到终态。是否执行要看 Gateway 审计和 NavigationSim journal。 |
| "F0 会不会被骗？" | 自报身份不行（38 项反例）；但要注意新的信任假设：受信任配置、签发者资质、账本与核验代码的完整性。 |
| "DDS 拒绝是真的中间件拒绝吗？" | 是。S3/S4 有 Fast DDS 原生 `not found in allow rule` 日志，且 S3C 正向对照成功。 |
| "能检测未知攻击吗？" | 不能宣称。M1 是监督二分类且门槛未过；M3 是确定性规则引擎，不是未知攻击预测模型。 |
