## 1. 结论先行

| 判断 | 内容 |
|---|---|
| **不是创新** | 使用 Ed25519、使用 DDS Security / SROS 2、使用 nonce 防重放、PDP/PEP 分离、fail-closed 原则本身 |
| **属于系统集成** | 把"DDS writer GUID → 证书主体 → 请求摘要 → Ed25519 → F0 → Gateway 独立复核"串成一条可审计链 |
| **有实验证据的新增能力** | 在实验室 DDS（意图主题）上该链成立且双向失败关闭；F0 与 Gateway 构成两道**相互独立**的判定；P07 证明真实 M3 建议可在 F0 生效 |

## 4. 逐项对比：相同点、不同点、证据

### 4.1 与 SROS 2 / DDS Security

- **相同**：都以 X.509 参与者身份为信任起点；都依赖 governance/permissions 表达资源权限。
- **不同**：SROS 2 回答"该参与者能否使用该 topic"；RosSystem 追问"这条请求是否由该参与者发出、内容是否被改、是否新鲜、是否应被执行"。
- **证据**：M2 17/17（`artifacts/acceptance/exports/m2_lab_identity_v110`）；Gateway 14/14（`m2_gateway_identity_v110`）。
- **边界**：只到意图主题，不是 Action。

### 4.2 与 DDS Security+（TPM 远程证明）

- **相同**：都试图把"身份"从"证书持有者"推进到"可验证的实体"。
- **不同**：DDS Security+ 证明**软件栈完整性**（平台可信），RosSystem 证明**当前请求归属与内容**（请求可信）。二者维度正交，可组合。
- **证据**：DDS Security+ 以 Tamarin 验证并以 Fast DDS 分支实现 [6]；RosSystem 以实验室双客户端零串号验证。
- **诚实表述**：不能写"RosSystem 比 DDS Security+ 更强"，只能写"解决不同层面的问题"。

### 4.3 与 DDS Security 形式化分析

- **关系**：Wang 等发现权限文件冒充、DoS、降级、隐私泄露 [5]，说明 DDS 层授权存在已知攻击面。
- **RosSystem 的定位**：不修复协议缺陷，而是在其上增加应用层证据与第二道判定，降低"单层被绕过即执行"的风险。
- **边界**：若攻击发生在 DDS 协议层（如权限文件冒充），RosSystem 的 M2 并不能修复，只能通过 F0/Gateway 的独立核验提高门槛。论文不得声称防御了 [5] 中的攻击。

### 4.4 与 ROS 2 入侵检测研究

- **关系**：ROSIDS23 等提供数据集与流量特征 [29]；Sommer/Paxson、Axelsson 等指出 ML IDS 的方法学陷阱 [8][9]。
- **RosSystem 的定位**：M1 只是**建议性证据源**，且当前 `validation_gate_passed=false`；论文不主张 IDS 能力，而是把 M1 的失败作为"证据不足时系统应如何决策"的案例。
- **证据**：`modules/member1_comm/model/comm_risk_model.json`；`paper/M1_RESEARCH_FINDINGS.md`。

### 4.5 与零信任 / ABAC / 多机器人授权框架

- **相同**：都强调逐请求、按属性/策略判定，而非一次性边界信任。
- **不同**：零信任与 ABAC 给出**架构与策略模型**，但不提供 ROS 2 中"请求内容如何被密码学绑定"的实现；Salimi 等的框架解决多机器人策略冲突 [24]，但不含密码学请求证明。
- **RosSystem 的补充**：把策略判定（Gateway TaskPolicy，未修改）与密码学身份门组合，并保持两者审计分离。

| 工作 | 相似点 | 核实状态 | 对本项目新颖性的影响 |

| DDS Security+ [6] | 增强 DDS 身份可信度 | 已核实（DOI + 摘要） | 不冲突：层面不同（平台 vs 请求） |

## 6. 可以写与不可以写

### 6.1 建议表述（有证据支持）

- "现有研究分别在 DDS 参与者认证、策略供给、远程证明与入侵检测方面形成了成熟方法；本文进一步探索把这些证据在**一次 ROS 2 任务执行准入**中做系统集成，并以正负对照与可审计证据验证其成立范围。"
- "在**临时实验室 CA、固定域、单一 DDS 实现**条件下，本文验证了从 DDS 主体到请求摘要的 Ed25519 绑定（**意图主题**）以及 F0/Gateway 双层独立阻断。"
- "本文的 Action `send_goal` 请求级身份绑定**未获验证**，原始 DDS reader 会破坏 Action 服务发现，这一负结果本身构成工程贡献。"
- "本文的 M1 模型**未通过部署门槛**，因此系统在证据不足时输出 UNKNOWN 并拒绝正向准入。"

## 7. 贡献分层（供论文 Contributions 小节直接改写）

**C1（系统集成，已部分验证）**
把中间件层主体身份与应用层请求内容绑定为一条可审计证据链，并在**意图主题**上以双客户端零串号验证（17/17）。**不含** Action 级。

**C2（机制实现，已验证）**
基于 Ed25519 的当前请求证明：摘要覆盖 `request_id/resource/operation/task_id/target`，配 nonce 原子账本与新鲜度窗；篡改/重放/过期/错主体/错目标失败关闭。**算法本身非创新**。

**C3（架构，已验证）**
F0 与 Gateway 的**双层独立授权**：F0 自行核验不读模块自报，Gateway 用自己的公钥/清单/nonce 账本重建摘要再核验，再交给未修改的 TaskPolicy；`GatewayIdentityCheck` 与 `DecisionEvent` 分离审计（14/14）。

**C4（方法学，已验证）**
可复现的安全实验与证据治理：正负对照 DDS 实验（7/7、6/6）、非秘密证据归档、主动勘误（P07）、负结果保留（Action reader、500 Hz 未检出）。

**C5（负结果与边界，已验证）**
明确记录"哪些没有做成"：Action 级绑定失败、M1 门槛未过、LEVEL 3 阻断。这构成 Threats to Validity 的一手材料。
