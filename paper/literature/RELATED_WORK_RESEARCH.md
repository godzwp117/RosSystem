## 1. ROS 2 基础通信安全：从"能通信"到"安全通信"

### 1.1 已有研究解决了什么

ROS 1 的通信模型默认明文、无认证、无授权，任何能接入网络的节点都可以发布或订阅话题。Dieber 等系统梳理了这一攻击面及其加固路径 [3]，构成 ROS 安全研究的起点。ROS 2 改以 DDS 为默认中间件，把认证、加密与访问控制下沉到中间件层，并通过 SROS 2 工具链把密钥与权限配置工程化 [1][2]。

Macenski 等给出 ROS 2 的设计与架构全景 [17]，Al-Batati 等 2026 年的系统性综述进一步把 ROS 2 相对 ROS 1 的技术演进、挑战与生态做了综合梳理 [18]。国内方面，鲁敬敬等的综述从机密性、完整性、可用性三个维度比较了 ROS 安全方案，并指出"安全性仍未得到足够重视" [7]。

### 1.2 主要技术路线

| 路线 | 代表工作 | 作用层 | 典型产物 |
|---|---|---|---|
| 中间件内建安全（DDS Security） | [1][2][32][33] | 参与者 / 资源 | 证书、governance、permissions、加密插件 |
| 策略程序化供给 | [1] | 参与者 / 资源 | 由接口推导的权限文件 |
| 可用性工程（DevSecOps） | [2] | 工具链 | keystore、enclave 划分、密钥分发 |
| 安全评估与攻击面枚举 | [19][20][4] | 系统 | 攻击向量、缓解效果、残余风险 |

### 1.3 代表工作与研究限制

- **代表工作**：White 等的策略程序化供给 [1]、Mayoral-Vilches 等的 SROS 2 工具 [2]、Sandoval 与 Thulasiraman 对 ROS 2 空中网络的攻击评估 [20]。
- **实际限制**：
  1. 这些机制保护的是**通信参与者与资源**，判据是"这个参与者能否发布/订阅这个 topic"；
  2. Sandoval 等虽证明 ROS 2 能缓解所选攻击向量，但同时观察到**可测量的运行延迟** [20]——安全不是零成本；
  3. White 等证明**启用安全后仍可被侦察** [4]；
  4. 国内综述 [7] 亦指出方案多在通信层，系统性仍在建设中。

### 1.4 RosSystem 能提供的（有证据）补充

RosSystem 不重复实现通信安全，而是把 SROS 2 / DDS Security 当作**第 1 层**，并在其上叠加应用层证据与准入。其可验证的贡献不是"更安全的 DDS"，而是**在实验室条件下把 DDS 层的主体身份与一次具体请求关联起来，并由第二个独立组件复核**（C1–C3，见 `NOVELTY_COMPARISON.md`）。

### 1.5 RosSystem 也没有解决的问题

- 仍是**单一 DDS 实现（Fast DDS 2.14）、单一 RMW、单一 ROS 发行版（Jazzy）**；
- 实验室 CA 不是生产信任根，无 HSM、无 CRL/轮换；
- 未做跨主机、NAT、不同内核的发现与安全验证。

## 2. DDS 参与者认证与资源授权：能力边界在哪里

### 2.1 已有研究解决了什么

DDS Security 规范定义了安全模型与 SPI 插件架构（认证、访问控制、密码学、日志、数据标记）[32]。在 ROS 2 语境中，规范被具体化为：每个 **DomainParticipant** 持有 X.509 身份，governance 与 permissions 文档以签名 XML 形式绑定到该参与者 [36]；ROS 2 进一步引入 **enclave**，规定"一个 participant 只能使用一个安全身份"，因此同一进程内多个节点必须共享同一套凭据 [35]。

Fast DDS 2.14 的实现文档明确了三个层次：参与者认证（DDS:Auth:PKI-DH）、实体访问控制（DDS:Access:Permissions）、数据加密（DDS:Crypto:AES-GCM-GMAC），并注明数据标记插件**尚未实现** [37]。

### 2.2 主要技术路线

| 路线 | 代表工作 | 关注点 |
|---|---|---|
| 规范与架构 | [32][33] | 安全模型、插件接口、治理/权限文档 |
| 形式化分析 | [5] | 协议安全目标是否可达、是否存在攻击 |
| 可信根增强（远程证明） | [6] | 对端软件栈完整性 |
| 配置与开销评估 | [21] | 互操作性、开启安全后的性能代价 |

### 2.3 关键结论与限制（论文可直接使用的三条）

1. **DDS 认证的对象是参与者，不是请求。** ROS 2 官方设计文档明确："a Participant can only utilise a single security identity"，并指出组合场景下存在"中间件凭据与实际可访问资源不匹配"的问题 [35]。
2. **权限判定的攻击面已被形式化工作证实。** Wang 等用 ProVerif 建模 DDS Security，自动确认了已知漏洞并发现权限文件冒充、拒绝服务、降级、隐私泄露四类新攻击 [5]。这说明 DDS 层授权是必要的，但不是充分的。
3. **DDS Security 不验证代码完整性。** Wagner 等指出参与者认证与访问控制不覆盖对端软件栈，需引入 TPM 远程证明并以 Tamarin 验证 [6]。这为"身份可信"增加了新维度，但仍停留在参与者/平台级。

### 2.4 与 RosSystem 的技术对比

| 维度 | DDS Security [32][35][37] | DDS Security+ [6] | RosSystem M2 |
|---|---|---|---|
| 被认证对象 | DomainParticipant | Participant + 软件栈测度 | Participant + **当前请求摘要** |
| 授权粒度 | topic/service 等资源 | 资源 + 平台完整性 | **资源 + 操作 + 任务参数（target/frame/坐标）** |
| 新鲜度 | 会话/握手级 | 握手级 | **每请求 nonce + 时间窗** |
| 请求内容完整性 | 不覆盖应用语义 | 不覆盖应用语义 | **request_digest 覆盖任务字段** |
| 验证者 | DDS 插件 | DDS 插件 + TPM | **F0 与 Gateway 各自独立核验** |
| 证据形态 | 中间件内部状态 | 握手内证明 | **文件 side channel + 审计事件（非协议内字段）** |

### 2.5 RosSystem 也没有解决的问题

- 绑定只发生在**预准入意图主题** `rt/m2/candidate_task`，**不是** Action `send_goal` 服务请求；
- 证明经**文件 side channel** 传递，文件系统在 TCB 内，不是 Action 协议内签名字段；
- 不修复 DDS 规范层缺陷（[5] 所述攻击不在 RosSystem 的防御范围内）。

## 3. 应用层身份与请求完整性：从"谁在通信"到"谁在请求什么"

### 3.1 已有研究解决了什么

这一脉络的核心问题是：**中间件层的身份能否直接解释为应用层某次请求的归属？** 现有工作从三个方向推进：

1. **威胁面刻画**：White 等证明 secure DDS 仍可被侦察与挖掘 [4]；
2. **可信根增强**：Wagner 等以 TPM 证明参与者软件栈 [6]；
3. **零信任与持续验证**：NIST SP 800-207 提出以 PDP/PEP 分离、逐请求授权、持续评估为核心的零信任架构 [40]；国内综述系统梳理了身份与访问管理、微分段、软件定义边界三条技术路线 [30]；ABAC 标准给出了以属性为中心的授权模型 [41]。

### 3.2 与"请求级绑定"最接近的工作

| 工作 | 绑定对象 | 与 RosSystem 的差异 |
|---|---|---|
| DDS Security [32][35] | Participant | 无请求内容、无逐请求新鲜度 |
| DDS Security+ [6] | Participant + 软件栈 | 证明的是平台，不是请求 |
| NIST ZTA [40] | 主体/资源/会话 | 架构级原则，未给 ROS 2 实现 |
| ABAC [41] / 多机器人 ABAC 框架 [24] | 主体与资源属性 | 策略模型，不含密码学请求绑定 |
| RosSystem M2 | Participant + 请求摘要 | 已实现但**仅意图主题**，非 Action |

> **必须如实报告的高度相关工作**：检索中发现一份日本机器人学会（RSJ）会议报告，标题为
> 「SROS2 with OIDC (OpenID Connect) — サービスロボットに対する命令の信頼性を担保する技術」，
> 其主题（用 OIDC 保障服务机器人指令的可信性）与 RosSystem 的应用层命令认证目标接近。
> **但该 PDF 返回 HTTP 403，作者、年份、方法与结论均无法核实**，因此本资料库
> **不将其列入正式参考文献**，仅在 `SOURCE_VERIFICATION_REPORT.md` 的"待核查清单"中登记。
> 论文作者在投稿前应设法获取该文并重新评估新颖性表述。

### 3.3 关键结论

- "DDS 已认证"**不能**推出"当前请求由该主体发出"；
- 请求级绑定需要三个要素同时成立：**主体 → 消息（GUID/证书）**、**消息 → 内容（摘要）**、**内容 → 新鲜（nonce/时间窗）**；
- 现有文献中，三者同时落到 ROS 2 部署并被实验验证的工作**在本轮检索范围内未发现**——但这是一个**有检索边界**的否定性判断，不能写成"尚无人研究"。

### 3.4 RosSystem 能提供的（有证据）补充

- C1：在实验室 DDS 中，把 `writer_guid → 证书主体 → request_digest → Ed25519 → F0` 串成可审计链，17/17 检查项通过，两个不同证书客户端零串号；
- 负向能力：篡改、重放、过期、错主体、错目标均失败关闭；
- **阴性结果**：Action `send_goal` 请求级绑定 **NOT_VERIFIED**——手工构造的 `TopicDataType` reader 会破坏 Action 服务发现（Planner 报 `NO_ACTION_SERVER`），同栈对照为 `EXECUTED`。

### 3.5 RosSystem 也没有解决的问题

- Action 级绑定需要 `rmw_fastrtps_cpp` 精确类型对象/TypeObject 或 service introspection 路径，尚未成功；
- 未实现凭据轮换、撤销与生命周期管理；
- 未处理 TOCTOU：从"证据通过"到"下游执行"之间授权状态可能失效，当前只有审计记录，没有原子性保证。

## 4. 多源安全证据与分层决策：如何让不同维度的证据共同参与一次准入

### 4.1 已有研究解决了什么

- **风险自适应访问控制**：Cheng 等提出"量化风险"的自适应访问控制并进行实验评估 [23]；
- **属性/策略驱动的多机器人授权**：Salimi 等提出可定制的冲突消解 + ABAC 框架，面向多机器人系统 [24]；
- **多源信任修正**：Jøsang 等讨论多源信任信息的修正与融合 [25]；
- **执行监控与运行时强制**：Schneider 给出可执行策略的理论边界 [14]；Lanotte 等把运行时强制用于控制系统安全 [28]；
- **零信任架构**：PDP/PEP 分离与持续评估 [40]，国内综述 [30]。

> 说明：本轮还检索到跨层安全风险评估、Dempster–Shafer 证据融合等工作，但它们是面向电力 CPS、
> 网络态势评估等不同领域的方法学，与本项目"ROS 2 任务准入"的证据链不能直接类比，
> 故未列入正式引用，只在检索记录中保留。

### 4.2 关键研究问题与现有答案

| 问题 | 现有认识的回答 | 证据 |
|---|---|---|
| 多源证据如何进入统一判断？ | 可用策略/属性模型表达，但"证据可信度"本身需要建模 | [23][24][25][41] |
| 身份、通信风险、任务风险是否同一维度？ | 不是。它们对应不同的失效模式与不同的判据 | [5][8][40] |
| 证据缺失时如何决策？ | 原则上有 fail-safe 默认；代价是可用性 | [15] |
| 分层授权能否降低单层失效？ | 能降低"单层误判直接导致执行"的概率，但不能消除共因失效 | [14][40] |
| 建议性风险 vs 权威性策略 | 必须区分：前者是输入，后者是判定 | [40] |

### 4.3 RosSystem 的对应关系（必须写清楚）

| 组件 | 证据类型 | 权威性 | 是否可单独放行 |
|---|---|---|---|
| M1 | 通信风险（模型输出，含 UNKNOWN） | **建议性** | 否 |
| M2 | 当前请求身份（GUID→证书→摘要→Ed25519） | 证据性 | 否 |
| M3 | 任务风险（区域/策略建议） | **建议性** | 否 |
| F0 | 联合准入（自行核验，不读模块自报） | **判定性** | 是（在其作用域内） |
| Gateway | 独立身份门 + TaskPolicy | **判定性** | 是（在其作用域内） |

RosSystem 的可验证主张是：**F0 READY ≠ Gateway ALLOW**，两层各自独立核验，且阻断可归因（G1 ALLOW/1 Goal；G2/G3 BLOCK/0；G4 身份 ALLOW 但 TaskPolicy OUT_OF_REGION/0）。

### 4.4 RosSystem 也没有解决的问题

- 没有形式化的证据融合语义（例如证据冲突时的优先级、置信度传播）；
- fail-closed 的可用性代价未量化；
- 多层检查的**端到端**延迟未测（现有 30 次为组件级，p50 verify 1.40 ms）。

## 5. 机器人任务执行阶段的独立安全控制：研究缺口与既有尝试

### 5.1 已有研究解决了什么

- **任务/目标层的策略表达**：ABAC 与冲突消解框架已能表达多机器人任务级策略 [24]；
- **运行时强制**：控制系统的运行时安全强制已有形式化与实现 [28]；
- **攻击面实证**：Quarta 等对工业机器人控制器进行了实验性安全分析，证明网络攻击可造成物理后果 [19]；
- **ROS 2 攻击评估**：Sandoval 等验证了 ROS 2 对特定攻击向量的缓解能力 [20]。

### 5.2 缺口判断（有限定条件）

在本轮检索范围内（Crossref 全库主题检索 + Semantic Scholar 摘要 + 出版方页面），
**未发现**把"应用层任务请求的密码学绑定"与"两层独立准入"同时实现并在 ROS 2 上做正负对照实验的公开工作。
但必须同时声明检索边界：

- 未覆盖 IEEE Xplore / ACM DL 全文库的站内检索（仅经 DOI/摘要）；
- CNKI 仅能核实题录与摘要，未做全文检索；
- 一份疑似高度相关的工作（SROS2 + OIDC）无法访问；
- OpenAlex 主题发现因配额耗尽而受限。

因此论文只能写"**在本文检索范围内**，现有工作分别针对……；本文进一步探索……的系统集成与可审计验证"，不能写"尚无研究"。

### 5.3 RosSystem 能提供的（有证据）补充

- P07：真实 M3 在**受控隔离**配置下给出 `BLOCK_RECOMMENDED / OUT_OF_REGION`，F0 产生 `ADAPTER_BLOCK`，Planner `submitted=false`，13/13；
- 三真实负向：LEVEL 1/2 PASS，LEVEL 3 **BLOCKED**（M1 UNKNOWN），未用 Mock 替换；
- Gateway 双层：14/14，身份门与 TaskPolicy 分别审计。

### 5.4 RosSystem 也没有解决的问题

- P07 的 M1/M2 为 **MOCK**，只隔离 M3，不等于三真实链；
- 三真正向 LEVEL 3 仍 BLOCKED；
- 只覆盖固定导航任务与固定 TaskPolicy，不能外推到其他任务族。

## 6. 安全证据审计与实验可复现性：让结论可被复查

### 6.1 已有研究解决了什么

- **日志与审计**：NIST SP 800-92 给出日志管理与审计的基本实践，包括日志生命周期、留存与访问控制 [47]；
- **可复现性方法学**：Munafò 等提出可复现科学的若干措施（方法、报告、注册、数据与代码共享）[46]；
- **统计报告**：Wilson 区间 [42]、Brown 等对二项比例区间估计的比较 [43]、Benjamini–Hochberg 多重比较校正 [45]、Chow 的拒识（reject option）理论 [44]；
- **分组验证**：Roberts 等系统讨论具有时间/空间/层级结构数据的分组交叉验证 [26]；Gama 等综述概念漂移 [27]。

### 6.2 关键结论

1. 小样本全通过必须给区间，不能给"高可靠"断言 [42][43]；
2. 多场景多指标必须考虑多重比较 [45]；
3. 会话/分段结构数据必须分组验证，否则泄漏导致乐观偏差 [26][10]；
4. 证据必须可定位：路径、哈希、运行环境、退出码。

### 6.3 RosSystem 的实践（可写为方法学贡献）

- `paper/CLAIM_EVIDENCE_MATRIX.csv` 把每条主张绑定到证据路径与允许措辞；
- `paper/FINAL_PACKAGE_REPRODUCTION.md` 记录 SHA-256、容器、命令与结果；
- 主动纠错：P07 原证据不成立时发布 `paper/ERRATUM_P07.md` 并重做实验；
- 明确标注 `ORIGINAL_FULL_PYTEST_LOG = NOT_RECOVERED`，不用新日志冒充原始日志。

### 6.4 RosSystem 也没有解决的问题

- 第三方主机复现 **NOT_RUN**；
- 最终包的原始完整 pytest 日志不可恢复；
- 未做统计功效分析与多重比较校正（这一点应在 Threats to Validity 中明确承认）。

## 7. 小结：研究脉络与 RosSystem 的位置

```text
[通信安全]  SROS2 / DDS Security  ──────────────► 已成熟，RosSystem 直接复用
      │
[身份边界]  Participant 级身份 ──► 远程证明 [6] ──► 仍非请求级
      │
[请求绑定]  RosSystem M2（意图主题）──► 负结果：Action 级未打通
      │
[分层决策]  风险自适应/ABAC/ZTA ──► F0 + Gateway 双层独立判定（有证据）
      │
[任务准入]  运行时强制/策略框架 ──► P07 受控隔离阻断（M1/M2 MOCK）
      │
[可审计性]  证据矩阵 + 复现记录 + 勘误 ──► 方法学实践
```

**一句话定位**：现有研究分别在通信安全、参与者身份、策略模型与入侵检测上形成了成熟方法；RosSystem 的探索集中在**把这些维度在一次 ROS 2 任务执行准入中做系统集成，并以正负对照与可审计证据验证其成立范围**——同时明确它在 Action 级身份、M1 可信模型与生产部署上尚未成立。
